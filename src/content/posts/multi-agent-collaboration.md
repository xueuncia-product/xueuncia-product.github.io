多接一个 Agent，并不自动让工作更快。我遇到过两个 Agent 各自完成同一个需求，最后出现两套应用和两套数据的情况。两边都在忙，结果却不能接起来。

后来我更在意三个问题：谁负责最终交付，大家依据的是不是同一份事实，以及下一方拿到材料之后知不知道该做什么。

本文整理自我的多 Agent 协作与知识库实践，于 2026 年 10 月 10 日改写为公开版。目录名称是可选习惯，不是一套必须照搬的安装配置。

## 一个交付物，只设一个负责人

开工前先读任务入口和当前状态，再认领工作。一个人或 Agent 维护最终交付物，其他参与者完成独立部分或写审查意见。

“有人在做”与“已经有人负责”不是一回事。分工需要具体到产物和写入位置，否则两个 Agent 很容易以为自己都应该补完整套流程。

发现事实或口径错误，回到原位置修正，不在各自产物里另写一套。计划和协作约定变化较慢，运行状态变化较快，可以分别维护，避免一长串进度把契约淹没。

## 目录可以表达协作边界

我会区分输入、交付物、原始过程和复用工具。它们回答的问题不同：

| 内容 | 它回答什么 |
|---|---|
| 已确认上下文 | 当前应该依据哪些事实和约束 |
| 最终交付物 | 接下来要使用哪个结果 |
| 原始记录 | 当时怎样讨论、失败和作出决定 |
| 复用工具 | 下次可以重复执行哪些动作 |

已有项目结构优先，不为了统一名字破坏脚本和引用。重要的是边界清楚，以及入口能把参与者带到正确位置。

## 归档和记忆分层

完整归档适合事后检索，精炼记忆适合下次开工。把每段日志都塞进记忆，往往只会让任务越来越重。

我更愿意在记忆里保留稳定规则、关键决定、确认过的偏好和当前项目入口。历史数字、详细进展、工具输出与大附件留在对应资料里，用索引连接。

共享记忆不存凭据。是否能同步到云端，要按资料范围和授权决定。旧用量和旧运行状态，也不能代替当前事实。

## 交接包要让下一方能直接开工

阶段结束时，我会留下一个短交接：目标、已确认事实、有效结论、证据位置、未决事项和下一步。

交接还需要说明材料用途和限制。例如另一方已经完成了一套素材，下一方应该明确复用，而不是重新抓一套；一方负责主稿，另一方就把审查反馈留在独立位置。

任务目标和验收也应写在前面。只有会影响范围或正确性的缺口才追问；明确的小任务直接执行。已有授权的范围不反复确认，新的重要写入和对外行动有具体授权。

## 先用一次小协作验证规则

协作契约写得漂亮，不等于真的生效。第一次合作时，检查参与者有没有读入口、有没有认领任务、有没有守住负责人和写入边界。

规则失效时修入口或规则，不只是再积累一份没人读取的说明。排错也一样：相同错误没有新证据，就不继续重读全部日志；周期任务和排障会话分开，避免不断继承越来越长的上下文。

我现在判断一次多 Agent 协作是否成功，会看结果能不能接起来、事实有没有分叉、交接有没有减少重复劳动。并行只是手段，清楚的事实与责任才让并行有用。
